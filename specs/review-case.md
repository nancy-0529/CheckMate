# Expense Case Review｜費用案件初審

> 本文件定義「案件初審分析」的產品需求與驗收標準，作為後續 AI 協作、設計與工程實作的共同依據。技術架構、API、資料庫與程式模組設計不在本文件範圍。

## 1. Objective

### Background / Problem

財務／會計初審人員需要逐筆核對申請資料、佐證、企業規範與必要的合規要求，才能判斷案件是否可通過、需要補件或需要人工進一步確認。

目前主要問題是：

- 檢查項目分散，容易因案件量、經驗差異或人工疏漏而漏查。
- 若系統只給結論、沒有規則與佐證依據，使用者仍需重新人工核對。
- 同一案件重新審查後，若無法保留歷程與判斷依據，後續難以追溯。

### Goal

在取得一筆可供審查的結構化費用案件後，CheckMate 能：

1. 完成必要的初審檢查。
2. 清楚呈現檢核結果與需要注意的問題。
3. 形成一致的案件層級審查建議。
4. 讓使用者快速理解「檢查了什麼、發現了什麼、依據是什麼」。
5. 保存每次審查結果與依據，不覆蓋歷史。

### User Story

As a 財務／會計初審人員

I want CheckMate 自動完成一筆費用案件的必要檢查，並清楚呈現審查建議、關鍵問題與依據

So that 我能快速驗證結果，把時間集中在真正需要人工判斷的案件。

## 2. Scope

### In Scope

- 可供審查的結構化案件資料。
- 代表性 Mock Cases，涵蓋正常、缺件、金額不一致、超額、疑似重複與無法判斷等情境。
- 四個核心審查面向：
    - 佐證比對
    - 企業規範
    - 有限範圍的合規檢查
    - 基礎風險訊號
- 檢核結果、發現項目與審查建議。
- 規則與佐證的可追溯性。
- 審查紀錄與重新審查歷程。

### Out of Scope

- 資料上傳、OCR、真實外部系統串接。
- 憑證真偽判斷。
- 合理性／情境風險模型。
- 補件、人工執行、PROCEED／REQUEST_INFO／ESCALATE／OVERRIDE 等後續流程。
- 完整台灣法規知識庫。
- 自動執行前的 Independent Verification。
- 正式 UI 實作。介面先以 Prototype 驗證資訊層級與易用性，不在此 Spec 展開。

## 3. User Flow

**起點**：財務初審人員開啟一筆已完成初審分析的案件。

**終點**：使用者理解目前的審查建議、關鍵原因與依據；若案件曾重新分析，也能理解本次與前次的主要變化。

```
開啟案件
↓
查看最新審查建議＋關鍵原因
↓
是否有需要注意的發現？
├─ 無
│  → 明確知道必要檢核已完成且無異常
│  → 如有需要，可查看各項檢核結果
│
└─ 有
   → 查看關鍵發現
   → 需要更多資訊時，查看規則／佐證／對照案件
   → 若有無法判斷項目，明確知道哪些部分需要人工確認
↓
是否曾重新審查？
├─ 否 → 完成
└─ 是 → 查看本次與前次的關鍵變化
          → 必要時查看完整審查歷程
↓
完成
```

### 資訊呈現原則

- **結果優先**：先看到審查建議與造成建議的關鍵原因。
- **依據可驗證**：每個需要注意的問題都能回到具體規則、佐證或對照案件。
- **逐步揭露**：規則全文、原始佐證與歷史紀錄需要時再查看。
- **不確定性明示**：「已確認有問題」與「系統無法判斷」必須清楚區分。

### 3.1 代表案例（Mock Cases）

本次至少準備以下代表案例，且所有案例使用同一套資料結構與審查模型；後續可增加案例，但不應為每個案例建立獨立判斷邏輯。

| # | 情境 | 主要驗證 | 預期建議 |
| --- | --- | --- | --- |
| 1 | 正常案件 | 所有必要檢核完成且無異常 | 建議通過 |
| 2 | 缺少必要佐證 | 缺漏可被辨識並指出缺少項目 | 建議補件 |
| 3 | 申請金額與佐證金額不一致 | 資料不一致可被定位與解釋 | 建議人工審核 |
| 4 | 超出企業規範上限 | 能引用對應企業規範 | 建議人工審核 |

## 4. Acceptance Criteria

### 4.1 正常案件

**Given** 一筆所有必要且適用檢核均完成，且沒有發現異常的案件

**When** 完成初審分析

**Then**

- 審查建議為「建議通過」。
- 使用者能確認必要檢核已完成。
- 不產生需要注意的 Finding。
- 不得以「沒有內容」代表已通過。

### 4.2 缺少必要佐證

**Given** 一筆缺少可補正必要佐證的案件

**When** 完成初審分析

**Then**

- 產生對應的缺漏 Finding。
- Finding 清楚指出缺少什麼。
- 使用者能看到對應規則或判斷依據。
- 審查建議為「建議補件」。

### 4.3 申請金額與佐證金額不一致

**Given** 一筆申請金額與佐證金額合計不一致的案件

**When** 完成初審分析

**Then**

- 產生「金額不一致」Finding。
- 顯示申請金額、佐證金額與差異依據。
- 不得標示為通過。
- 審查建議為「建議人工審核」，不設容許誤差區間；待累積足夠實際案例後，再評估是否依差異原因或可補正性另訂規則。

### 4.4 違反企業規範

**Given** 一筆資料完整，但不符合適用企業規範的案件

**When** 完成初審分析

**Then**

- 產生對應 Finding。
- Finding 指出不符合的規則與實際案件值。
- 使用者可回溯至規則名稱／版本／條件。
- 審查建議為「建議人工審核」。

### 4.5 疑似重複申報

**Given** 一筆案件符合重複申報判斷條件

**When** 完成初審分析

**Then**

- 產生「疑似重複申報」Finding。
- 使用者能看到被拿來比對的案件。
- 使用者能理解使用哪些條件判斷相似。
- 審查建議為「建議人工審核」。

### 4.6 合規檢查不符合

**Given** 一筆案件不符合本次已納入且具明確來源的合規規則

**When** 完成初審分析

**Then**

- 產生對應 Finding。
- Finding 僅描述系統實際能確認的客觀不符合事項。
- 使用者可回溯至規則來源與版本。
- 不得延伸成稅務、法律或真偽的最終認定。
- 審查建議為「建議人工審核」。

### 4.7 系統無法判斷

**Given** 某項必要檢核因資料不足、格式無法解析或超出目前規則能力而無法可靠判斷

**When** 完成初審分析

**Then**

- 該檢核不得標示為通過。
- 使用者能清楚看到「無法判斷」及原因。
- 呈現方式必須與「已確認有問題」有所區別。
- 審查建議為「建議人工審核」。

### 4.8 重新審查

**Given** 同一案件被重新執行分析

**When** 新的分析完成

**Then**

- 新增一筆 Review Record。
- 先前的 Review Record 不得被覆蓋。
- 案件預設顯示最新一次審查結果。
- 使用者可查看 Recommendation 是否改變、新增 Findings 與已解決 Findings。
- 使用者仍可查看完整歷史紀錄。

### 4.9 一致性與可追溯性

- 每個 Finding 至少能回溯至一個具體判斷依據。
- 同一輸入與同一規則版本，應得到一致的檢核結果與審查建議。
- 所有 Mock Cases 使用同一套產品模型與規則，不為個別案例建立特殊邏輯。

## 5. Feature Spec

### 5.1 Structured Case Input

一筆可供審查的案件至少包含：

- 案件編號
- 申請人
- 費用類別
- 申請金額與幣別
- 費用發生日期
- 提交時間
- 申請說明
- 一筆或多筆佐證資料

佐證資料至少能提供目前審查規則需要使用的欄位，例如：

- 供應商
- 金額
- 日期
- 憑證必要格式資訊

所有 Mock Cases 必須使用同一套資料結構。

### 5.2 Review Checks

每筆案件依適用條件執行以下四個審查面向：

#### 佐證比對

確認申請資料與佐證是否一致、必要佐證是否齊全。

本次至少涵蓋：

- 缺少必要佐證
- 申請金額與佐證金額不一致

#### 企業規範

確認案件是否符合企業自己的費用政策。

Demo 規則可涵蓋：

- 費用上限
- 必要附件
- 可報支類別
- 申報期限

實際採用的規則需具有明確條件，不得只用模糊描述。

#### 合規檢查

僅檢查本次明確納入、具有可信來源且可客觀判斷的外部規則。

若規則來源尚未確認，不得以「台灣法規遵循」對外宣稱；僅能作為 Demo Compliance Rule。

#### 基礎風險訊號

透過跨案件比對辨識值得人工確認的異常。

本次至少涵蓋疑似重複申報。

正式條件需明確定義，例如使用哪些欄位與時間範圍判斷相似。

為避免「檢查結果、問題、最終建議」混在一起，下面三節（5.3–5.5）把判斷結果分成三層，各自有明確用途：Check Result 記錄每項檢核有沒有做、Finding 記錄需要使用者注意的問題、Recommendation 是案件層級唯一的最終建議。

### 5.3 Check Result

每一項適用檢核都必須留下明確結果，不以沉默代表通過。

支援狀態：

- **通過**：已完成檢查，未發現問題。
- **未通過**：已完成檢查，發現明確不符合或異常。
- **無法判斷**：系統目前不能可靠下結論。
- **不適用**：該規則不適用於此案件。

### 5.4 Finding

只有需要使用者注意的檢核結果才形成 Finding，例如：

- 缺漏
- 不一致
- 規範不符合
- 疑似異常
- 無法判斷、需要人工確認

正常通過的檢核不產生 Finding，但必須保留 Check Result。

每個 Finding 至少包含：

- 發現了什麼
- 為什麼重要
- 判斷依據
- 對案件下一步的影響

### 5.5 Recommendation

案件層級只呈現一個審查建議：

- **建議通過**
- **建議補件**
- **建議人工審核**

基本推導原則：

1. 必要資訊缺漏，且可透過補充資料解決 → **建議補件**
2. 資料足夠，但存在明確違規、異常、風險，或系統無法可靠判斷 → **建議人工審核**
3. 所有必要且適用檢核均完成，且沒有會阻塞通過的 Finding → **建議通過**
4. 同時存在補件與人工審核條件時，暫以 **建議人工審核** 優先

Recommendation 與內部 Automation Gate／Execution Control 分開，不形成第二套使用者決策模型。

### 5.6 Traceability

每個 Finding 必須能回溯至對應依據：

- 企業規範 → 規則 ID／名稱／版本／條件
- 合規規則 → 規則來源與版本
- 佐證比對 → 對應佐證資料
- 疑似重複 → 被比較的既有案件與比對條件

不得只產生無法驗證的 AI 說明文字。

### 5.7 Review Record & History

每次分析都產生新的 Review Record，不覆蓋前一次結果。

Review Record 至少保存：

- 案件
- 審查時間
- 當次 Recommendation
- 當次 Check Results
- 當次 Findings
- Findings 對應的規則／佐證／對照案件
- 當次使用的規則版本或參照

若案件曾重新分析，系統需提供：

- 本次與前次 Recommendation 是否改變
- 新增 Findings
- 已解決／不再出現的 Findings

差異摘要只用於快速理解，不取代完整歷史紀錄。

## 6. Prototype 待驗證問題

目前階段是 Prototype，不需要驗證視覺風格，先回答：

1. 使用者能否第一眼理解 Recommendation 與最重要的原因？
2. 正常案件沒有 Finding 時，什麼資訊足以讓使用者相信「真的有檢查」？
3. Finding 展開後，規則、佐證與對照案件的資訊順序是否容易理解？
4. 「已確認有問題」與「系統無法判斷」是否能被明確區分？
5. 重新審查時，「本次差異」與完整歷程的資訊層級是否合理？

## 7. Open Questions

以下問題尚未定案，不應由工程或 AI Agent 自行補完：

- 本次 Demo 最終採用哪些 5–8 條企業規範，以及各自的明確條件。
- 疑似重複申報的 deterministic 判斷條件。
- 合規檢查要採用哪一條具有可信來源的真實規則與版本。
- Finding 是否需要正式的優先級／嚴重程度欄位。
