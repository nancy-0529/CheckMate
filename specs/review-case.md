# Review Case（案件初審分析）

> 本文件取代先前的草稿版本，作為「案件初審分析」這個核心 Product Slice 的正式 Spec，內容經與產品負責人逐項確認產品決策後收斂而成。

## User Story

As a 財務／會計初審人員（由 CheckMate Agent 代為執行初審分析）
I want 針對一筆已結構化的費用案件，自動完成必要檢查、產生可驗證的發現項目，並形成一致的審查建議
So that 我可以快速判斷這筆案件是否能直接通過、需要補件，或需要人工審核，而不是花在逐筆核對規則與憑證這種重複性工作上

## Context

### 這個情境要解決的問題

財務初審人員目前面對每一筆費用申請，要自己從頭做三件事：讀懂單據內容、逐條核對企業規範／法規、判斷這筆有沒有問題，而且全靠個人記憶與經驗，量一大就容易漏。

「案件初審分析」交付的核心價值不是「幫使用者做決定」，而是「把檢查這件事做完、做完整，並且用使用者能一眼驗證的方式呈現出來」，讓財務初審人員只需要：

1. 快速確認 Agent 檢查的過程與依據有沒有漏掉或錯誤（可驗證，不是照單全收）。
2. 把自己的專業判斷力留給真正需要判斷的例外案件。

### 本次 Slice 範圍

**要做：**
- 定義可供審查的結構化案件格式與代表性 Mock Cases。
- 定義四個核心審查面向：佐證比對、企業規範、有限範圍台灣法規遵循、基礎風險訊號。
- 定義各面向如何產生發現項目（Finding），以及發現項目如何形成最終審查建議（Recommendation）。
- 定義可追溯性與審查紀錄（Review Record）的保存方式。

**不做（本次 Slice 明確排除）：**
- 資料上傳、OCR、真實外部系統整合，本 Spec 假設案件已經是結構化資料。
- 憑證真偽判斷、合理性／情境風險模型。
- 補件、人工執行與後續 Workflow Action（PROCEED／REQUEST_INFO／ESCALATE／OVERRIDE 的實際執行）。
- 完整台灣法規引擎。
- Control Model 中的 Independent Verification（獨立驗證），這屬於「自動執行動作前的交叉檢查」，本次 Slice 只做到「產生審查建議」，還沒有到自動執行階段，留待後續談執行機制的 Slice 再展開。
- 使用者介面／畫面設計，本 Spec 只定義分析引擎的產品行為，介面待此 Spec 確定後另外先做 Prototype 驗證，不在此 Spec 展開。

## User Flow

> 站在財務初審人員「如何使用審查結果」的角度描述，不是系統內部處理步驟。本次情境的終點定義為：使用者理解目前的審查建議、關鍵原因與對應依據；補件、人工審核、PROCEED 等後續操作不在此流程內。

**起點**：財務初審人員開啟一筆已完成初審分析的案件。
**終點**：使用者理解目前的審查建議、造成這個建議的關鍵原因，以及每個原因對應的具體依據；若案件曾被重新分析，也理解這次與上次有什麼不同。

```text
使用者：開啟案件
系統：立即呈現「審查建議」＋「造成此建議的關鍵原因」重點（不需要使用者操作就先看到結論）

分支①：有無發現項目
├─ 無任何發現（建議通過）
│    系統：明確標示「四個面向都已檢查，沒有問題」
│    使用者：可到此為止；若仍想確認，可展開查看「檢查過哪些項目」
│    → 抵達終點
│
└─ 有一或多筆發現項目
     系統：先列出「是哪幾個發現造成這個建議」的重點清單
     使用者：點擊其中一個發現，要求展開細節

     分支②：這個發現是「可判斷」還是「無法判斷」
     ├─ 可判斷（違規／缺漏／風險／不一致）
     │    系統：展開完整依據，問題是什麼、嚴重程度、對應規則／佐證資料／對照案件
     │    使用者：可再展開查看原始佐證資料，或（風險訊號）查看被拿來比對的既有案件
     │    → 使用者理解這個發現的原因與依據
     │
     └─ 無法判斷（資料超出系統認得的範圍）
          系統：用明顯不同的呈現方式標示「系統無法判斷，需要人工直接看原始資料」
          使用者：理解這不是系統已經確認的問題，而是系統判斷不了，需要自己看
          → 使用者理解「這裡需要靠自己判斷，不是系統給的結論」

     （使用者可重複點擊展開其他發現項目，直到看完所有需要理解的原因）
     → 抵達終點

分支③：首次審查 vs 重新審查（與分支①②並行存在，不互斥）
├─ 審查歷程只有一筆紀錄（首次審查）
│    系統：不顯示任何「差異」相關資訊
│
└─ 審查歷程有兩筆以上紀錄（曾重新分析）
     系統：額外呈現「本次與前次關鍵差異」摘要（建議是否改變、新增／已解決的發現）
     使用者：看摘要就懂就到此為止；想看更早的完整紀錄，可展開完整審查歷程列表
     → 使用者理解「這次為什麼跟上次不一樣」
```

**關鍵設計原則：**

- 使用者一開始永遠先看到結論（建議＋關鍵原因），不需要操作就看得到；所有規則、佐證、歷史紀錄都是「主動展開才看到」的第二層，不會一次性攤開。
- 「可判斷」與「無法判斷」在使用者操作上走同一條路徑（都是點擊發現項目展開），但系統回應的呈現方式必須讓使用者一眼分辨這兩種狀態的差異。
- 「重新審查」的差異摘要獨立於「有無發現」判斷之外，兩者同時存在時都要呈現，不互相取代。

## Behavior

### 一、可供審查的結構化案件

一筆可供審查的案件至少包含：

- **案件基本資料**：案件編號、申請人、類別、申請金額、幣別、費用發生日期、提交時間、說明。
- **佐證資料**（可一筆或多筆）：供應商、金額、日期、憑證格式資訊（是否具備正確的統一編號欄位，供台灣法規遵循檢查使用）。

### 二、四個核心審查面向

四個面向彼此獨立，缺一個都會漏掉一種財務初審人員原本要自己想的檢查：

| 面向 | 回答的問題 | 可能結果 |
|---|---|---|
| 佐證比對（Evidence Matching） | 這筆申請跟附上的憑證，內容對得起來嗎？ | 一致／不一致（金額對不上）／缺漏（缺少必要憑證） |
| 企業規範（Corporate Policy） | 有沒有踩到公司自己訂的線？ | 符合／不符合 |
| 台灣法規遵循（Taiwan Compliance，有限範圍） | 有沒有踩到法規（而非公司內規）要求的形式？ | 符合／不符合 |
| 基礎風險訊號（Risk Signal） | 放進脈絡裡看，會不會有單看沒問題、跨案件比對才發現的異常？ | 無異常／疑似異常（例如疑似重複申報） |

四個面向共通的安全閥（見「六、系統不下結論的情況」）：只要輸入資料落在系統認得的範圍之外（例如類別是未知值、金額或日期格式無法解析），一律誠實標示「無法判斷」，不強行套用規則。

### 三、發現項目（Finding）的共同呈現原則

不論哪個面向，只要有話要說（包含「沒問題」），都要能回答：

- **有沒有發現問題**：包含「這一關已經檢查過，沒有問題」這個狀態要明確講出來，不能用沉默代表通過。
- **問題是什麼**：用一句人看得懂的話講清楚，不是規則代碼。
- **憑什麼判斷**：能回溯到具體依據，哪一條規範、哪一筆佐證資料、或哪一筆相似的既有案件。
- **嚴重到什麼程度**：供使用者判斷優先順序（不等於最終審查建議，見「四」）。

各面向的特殊之處：

- **風險訊號**的「憑什麼判斷」必須能讓使用者查證到「是被拿去跟哪一筆既有案件比對出來的」，不然這個發現無法被驗證，使用者只能選擇盲目相信或不信。
- **台灣法規遵循**的發現，用詞只能停留在「格式／形式完整性」層級（例如「憑證缺少統一編號欄位」），**不得使用任何帶有稅務或法律結論性質的字眼**（例如「不符合稅務認列要求」）。CheckMate 在這一關只做客觀的格式比對，不做「最終稅務認定」或「真偽判斷」，這兩者都在 Product Boundary 明確排除的範圍內。

### 四、審查建議推導規則

依「問題性質」分兩類，而不是依單一嚴重度分級：

1. 只要存在任一「違規／風險／疑似異常」類的發現項目（企業規範不符合、台灣法規遵循不符合、風險訊號疑似異常，含佐證比對的「金額不一致」）→ **建議人工審核**
2. 否則，只要存在「缺漏」類的發現項目（佐證比對缺少必要憑證）→ **建議補件**
3. 否則 → **建議通過**

補充決策：

- **金額不一致目前一律進人工審核**，不設定容許誤差區間（例如零頭捨入的小額差異）。這是現階段的簡化決策，先觀察實際案例樣態，之後有足夠資料再收斂容許區間規則，不在這次預先假設。
- 「缺漏」與「違規／風險」同時存在時，**人工審核優先**於補件。

### 五、可追溯性與 Review Record

- **審查建議完全由發現項目決定，不存在任何獨立生成的說明文字。** 「為什麼得到這個建議」的答案，就是「列出是哪些發現造成這個結果」，不是另外寫一段 AI 摘要，避免摘要邏輯與實際判斷邏輯兜不起來，反而降低可信任度。
- **建議通過的案件也要交代「四關都跑過、都沒問題」**，不能因為沒問題就什麼都不顯示。
- **建議補件／人工審核的案件，先呈現「是哪個發現造成這個建議」的重點，再逐步展開每個發現的完整依據**（不一次攤開所有細節）。
- **每次執行分析都會產生一筆新的審查紀錄（Review Record），附加到案件的審查歷程，不覆蓋或修改先前紀錄。**
- **案件目前顯示的審查建議，對應審查歷程中最新一筆紀錄；歷史紀錄需可完整查看。**
- **若案件曾被重新分析，額外提供「本次與前次的關鍵差異」作為輔助資訊**，內容為輕量級摘要（不做逐欄位比對）：
  - 審查建議是否改變（例如「上次：建議補件 → 這次：建議通過」）。
  - 哪些發現是新出現的、哪些是這次已經解決或不再出現的。

### 六、系統不下結論的情況

需要區分兩種完全不同性質的「轉人工」：

- **有明確發現的轉人工**：系統看得懂資料，套用規則後判斷出具體的違規或異常，只是需要人來拍板，這是系統做出了一個具體判斷。
- **系統看不懂資料而轉人工**：輸入本身超出系統認得的範圍（例如類別是未知值、金額或日期格式無法解析），規則根本套不上去。這種情況絕對不能包裝成「有具體發現」，必須誠實標示「無法判斷」，並在呈現用詞上與「有明確發現」清楚區分，讓財務初審人員知道自己被要求做的是「這件事系統做不到」，而不是「幫忙確認系統已抓到的問題」。

### 七、Control Mechanism 於本次 Slice 的落地範圍

Product Brief 的 Control Model 在本次 Slice 的對應方式：

- **Required Checks 是否完成**：由「三」與「五」落地，每個面向即使沒問題也要明確交代已檢查，不能沉默。
- **Evidence Chain**：由「三」與「五」落地，每個發現都能追溯到規範、佐證或既有案件，沒有腦補空間。
- **Hard Guardrail**：由「六」落地，看不懂的資料不強行套用規則，誠實標示無法判斷。
- **Independent Verification**：明確排除於本次 Slice（見 Context 的「不做」）。

### 八、台灣法規遵循的規則內容

**選定規則**：申請金額達到示範門檻（例如 NT$3,000，具體數字為 Mock Policy 資料，可調整不影響本 Spec 行為定義）以上時，若佐證資料未具備正確的統一編號憑證格式，則產生格式不完整的發現項目，轉人工確認；低於門檻，或憑證格式正確，則無此發現。

**邊界聲明**：這是示範用的簡化版本，門檻金額與判斷方式是為了 Demo 可明確判斷而簡化，不代表真實稅法的完整規定，也呼應「不建立完整台灣法規知識庫」的產品邊界。此檢查只判斷憑證格式的客觀完整性，不做任何稅務認列資格或憑證真偽的實質判定。

### 九、代表性 Mock Cases（6 筆）

| # | 情境 | 觸發面向 | 預期審查建議 |
|---|---|---|---|
| 1 | 正常案件 | 無 | 建議通過 |
| 2 | 缺少必要佐證 | 佐證比對（缺漏） | 建議補件 |
| 3 | 申請金額與佐證金額不一致 | 佐證比對（不一致） | 建議人工審核 |
| 4 | 超出企業規範金額上限 | 企業規範 | 建議人工審核 |
| 5 | 疑似重複申報 | 風險訊號 | 建議人工審核 |
| 6 | 金額超過門檻但憑證缺少統一編號 | 台灣法規遵循 | 建議人工審核 |

## Acceptance Criteria

- Given 一筆案件資料完整、金額與佐證一致、無政策違規、無風險訊號、憑證格式符合台灣法規遵循要求
  When 執行分析
  Then 產生審查建議「建議通過」，且四個面向皆明確標示「已檢查，無問題」

- Given 一筆案件缺少企業規範要求的必要佐證
  When 執行分析
  Then 產生一筆「缺漏」類發現項目，說明缺少的項目，審查建議為「建議補件」

- Given 一筆案件的申請金額與佐證金額不一致
  When 執行分析
  Then 產生一筆佐證比對的發現項目，審查建議為「建議人工審核」（不論差異大小，本階段不設容許區間）

- Given 一筆案件的申請金額超出對應類別的企業規範金額上限
  When 執行分析
  Then 產生一筆企業規範的發現項目，審查建議為「建議人工審核」

- Given 一筆案件與既有案件在申請人、供應商、金額、日期上高度相近
  When 執行分析
  Then 產生一筆風險訊號的發現項目，且該發現項目可回溯指出是與哪一筆既有案件比對，審查建議為「建議人工審核」

- Given 一筆案件金額超過示範門檻，且佐證資料缺少正確的統一編號憑證格式
  When 執行分析
  Then 產生一筆台灣法規遵循的發現項目，用詞僅描述格式完整性（不含稅務或法律結論字眼），審查建議為「建議人工審核」

- Given 一筆案件的類別欄位為系統無法辨識的值
  When 執行分析
  Then 產生一筆明確標示為「無法判斷」的發現項目（呈現方式與「有明確發現」不同），審查建議為「建議人工審核」

- Given 同一筆案件被重複執行分析兩次
  When 第二次執行完成
  Then 審查歷程包含兩筆紀錄，第一筆紀錄未被覆蓋，且提供本次與前次的關鍵差異摘要（建議是否改變、新增或已解決的發現項目）

## Edge Cases

- 同時存在「缺漏」與「違規／風險」類發現項目，依優先序，最終為「建議人工審核」。
- 案件完全沒有附上任何佐證資料，視為「缺漏」類發現項目，而非「不一致」。
- 案件沒有任何發現項目，建議通過。
- 「無法判斷」類發現項目不得與「有明確發現」類使用相同呈現方式或字眼，避免使用者誤判系統的確定性程度。

## 尚未定案、留待後續 Slice 的問題

- 佐證比對「金額不一致」是否需要容許誤差區間，目前一律轉人工，待累積實際案例後再議。
- Control Model 的 Independent Verification 如何在執行階段（PROCEED 等自動化）落地，留待對應 Slice。
- 介面呈現方式，本 Spec 只定義分析行為，介面另外先做 Prototype 驗證，不在此文件展開。
